# Detection heuristics

How to infer profile, path_filters, path_instructions, and tools from repo signals without asking the user.

## Step 0: Quick recon

Run these in parallel (Bash):

```bash
git rev-parse --show-toplevel                     # confirm repo root
git ls-files | head -500                          # file census
git log --format='%an' | sort -u | wc -l          # author count
git log --oneline | wc -l                         # commit count
ls -la                                            # top-level dirs and dotfiles
find . -maxdepth 2 -name "CLAUDE.md" -o -name "AGENTS.md" -o -name ".cursorrules" -o -name "CONTRIBUTING.md" 2>/dev/null
cat CODEOWNERS .github/CODEOWNERS 2>/dev/null
```

You're trying to answer: language(s), monorepo y/n, solo vs team, has CI, has public API.

## Profile inference

Default to `chill`. Flip to `assertive` only when the repo clearly benefits from detailed review:

| Signal                                              | Push toward |
|-----------------------------------------------------|-------------|
| Single author in `git log`                          | chill       |
| `< 50` commits total                                | chill       |
| CLAUDE.md says "move fast" or "side project"        | chill       |
| Multi-author (`>= 3` distinct authors)              | assertive   |
| Has `CODEOWNERS`                                    | assertive   |
| Has `.github/workflows/` with required checks       | assertive   |
| Library / SDK (presence of `package.json` with `"main"` + published name, or `setup.py` / `pyproject.toml` with a publishable package) | assertive   |
| Repo name contains `lib`, `sdk`, `api`, `core`      | assertive   |

If signals split: ask Q1. Otherwise: pick the inferred value silently and note it in the final summary.

## path_filters detection

Always exclude (no judgment needed):
```
!**/node_modules/**
!**/dist/**
!**/build/**
!**/out/**
!**/.next/**
!**/.nuxt/**
!**/.svelte-kit/**
!**/.turbo/**
!**/target/**             # Rust / Java
!**/vendor/**             # Go / PHP
!**/__pycache__/**
!**/*.pyc
!**/.venv/**
!**/venv/**
!**/coverage/**
!**/.coverage
!**/*.lock
!**/*.min.js
!**/*.min.css
!**/*.map                 # source maps
```

Conditionally exclude if you see them in `git ls-files`:
- `**/migrations/**/*.py` (Django) and `**/migrations/**/*.sql` (Rails-style) if they look autogenerated (timestamp prefixes).
- `**/*.pb.go`, `**/*.pb.ts`, `**/*_pb2.py`, `**/*_pb2_grpc.py` (protobuf-generated).
- `**/*.generated.{ts,go,py}` and any file with `generated` or `auto-generated` in the first 5 lines.
- `**/schema.graphql.d.ts`, `**/__generated__/**` (GraphQL codegen).
- `**/*.snap` (Jest snapshots).
- `**/fixtures/**`, `**/__fixtures__/**` (test data).

Don't exclude:
- `tests/`, `spec/`, `__tests__/` (CR review of test code is valuable).
- `docs/` unless huge.
- Migration files that look hand-written.

## path_instructions: lifting conventions from CLAUDE.md / AGENTS.md

Read the file(s). For each rule that's about *code* (not workflow), translate into a `path_instructions` entry:

| CLAUDE.md style rule                                          | path_instructions entry                                                                 |
|---------------------------------------------------------------|------------------------------------------------------------------------------------------|
| "No em-dashes anywhere"                                       | `{ path: "**/*", instructions: "Flag any em-dash (U+2014) in prose or comments." }`     |
| "Prefer functional React components"                          | `{ path: "**/*.{tsx,jsx}", instructions: "Flag class components; prefer functional." }` |
| "Always validate at system boundaries"                        | `{ path: "**/api/**", instructions: "Flag handlers that don't validate inputs at the boundary." }` |
| "No default exports"                                          | `{ path: "**/*.{ts,tsx}", instructions: "Flag default exports; prefer named exports." }` |
| "Tests must use real DB, not mocks"                           | `{ path: "**/*test*.py", instructions: "Flag database mocks in integration tests." }`   |

Skip rules that aren't reviewable (e.g., "discuss before building", "ask one question at a time"). CR reviews diffs, not workflow.

Cap at ~8 `path_instructions` entries. More than that, CR starts ignoring them. Pick the highest-signal rules.

## Monorepo detection and per-package instructions

Markers:
- `pnpm-workspace.yaml`, `lerna.json`, `nx.json`, `turbo.json` → JS/TS monorepo.
- `packages/`, `apps/`, `services/` as top-level dirs with their own `package.json`.
- Cargo workspace (`Cargo.toml` with `[workspace]`).
- Go workspace (`go.work`).

For each package with its own README or CLAUDE.md, add a path-scoped `path_instructions` entry:
```yaml
- path: "packages/billing/**"
  instructions: "This package handles money. Be strict about decimal precision and rounding."
```

If there are >5 packages, only add instructions for the ones with explicit per-package docs. Don't fabricate.

## Tools to enable

See `schema-notes.md` for the language→tool mapping. Rule of thumb: enable a tool only if the repo *already runs it locally* (has a config file like `.eslintrc`, `ruff.toml`, `.golangci.yml`, `.rubocop.yml`). Otherwise the first review becomes a wall of style noise.

## tone_instructions

Lift the *voice* part of CLAUDE.md, capped at 250 chars. Examples:

- "Direct, terse feedback. No em-dashes. Skip ceremony."
- "Be friendly and explain reasoning; this is a learning repo."
- "Match the bluntness of the existing code review style."

If CLAUDE.md doesn't have voice rules, leave `tone_instructions: ""`. Don't invent.

## Bail-out conditions

If detection produces nothing useful (empty repo, only README, no clear language), tell the user: "Repo is too thin to infer from. Want me to drop in a vanilla `.coderabbit.yaml` with just the universal path_filters?" and use the base template unchanged.
